# Brief de decisão Q-022 — E6: patch de estabilidade ou quarentena

Data: 2026-08-27
Status: `⛔ DECISION` — não aplicado por este brief
Escopo: comportamento de CI/readiness para o cenário E6.

## Contexto

O run remoto `33080843742` continua registrado como falha em T6/E6 no ref
histórico `develop@12c90a17`. Essa é evidência `STALE-OBSERVED`/histórica, não
uma execução do checkout atual. O harness local foi alterado de forma confinada
ao teste e passou 12/12 combinações de `E6_HOLD_MS` × `E6_QUEUE_MS`, sempre com
dois gateway calls, dois sucessos, seis rejeições de quota,
`peakActiveCalls=2`, `tokens_reserved=0` e `in_flight=0`.

O runtime, schema e migrations não foram alterados pelo patch E6. A evidência
local é `LOCAL-VERIFIED` para o executor, mas não comprova CI remoto, Neon ou
produção.

## Opções

| Opção              | Benefício                                                                                           | Custo/risco                                                                              |
| ------------------ | --------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| Patch do harness   | Remove a dependência de timing de wall-clock e preserva o gate de concorrência; permite novo verify | Precisa de novo run remoto em um head publicado para promover a evidência                |
| Quarentena no CI   | Mantém o vermelho visível e evita usar o cenário instável como bloqueio imediato                    | O readiness continua vermelho e a falha pode contaminar verify/C6; reduz a força do gate |
| Manter sem mudança | Não altera comportamento                                                                            | Preserva uma falha conhecida e não executa o plano v5.1                                  |

## Recomendação

Recomenda-se **aprovar o patch do harness**, limitado ao commit `test(e6)` e
sem mudança de runtime. A aprovação deve exigir um novo verify/CI em head
publicado, com captura de SHA exato, resultado, logs e digest. O patch não deve
ser usado para declarar E6 verde em `develop` até essa execução remota existir.

## Rollback

Reverter somente o commit do harness E6 e restaurar o cenário anterior; manter a
evidência do run remoto vermelho e marcar o problema como timing/harness ainda
não resolvido. Não reverter a lógica de reserva, settlement ou isolamento de
tenant, pois ela não é o objeto desta decisão.
