### 1.2 Passo 1 — `BETTER_AUTH_URL` para o canônico e `AUTH_TRUSTED_ORIGINS` com canônico **+ preview** (transição)

Valores (origens puras, HTTPS, **sem** path/busca/credencial/fragmento — a validação é fail-closed):

```text
BETTER_AUTH_URL        = https://diretrizprecifica.com
AUTH_TRUSTED_ORIGINS   = https://diretrizprecifica.com,https://<preview-host>
```

Regras de conteúdo (fonte de código, não de opinião):

- `parseOrigin` aceita **somente** `https:` fora de `localhost`/`127.0.0.1` e rejeita path/query/hash/
  usuário/senha (`src/server/auth/auth-policy.ts:12-29`).
- `AUTH_TRUSTED_ORIGINS` é **lista separada por vírgula**, cada item passado pelo mesmo `parseOrigin`
  (`auth-policy.ts:47-51`); `baseURL` entra automaticamente no conjunto de origens confiáveis
  (`auth-policy.ts:62-66`) — listar o canônico também é cinto-e-suspensório, não duplicação inútil.
- O **preview** fica no conjunto **apenas durante a transição** (é o alvo de rollback e de sondas
  comparativas); sai no fechamento (§4).
- Em produção o cookie de sessão é `__Host-preco_que_da_lucro.session_token` (`auth-policy.ts:67-69`).
  `__Host-` é **host-bound** (sem `Domain`): sessões abertas no preview **não** valem no canônico —
  todo login de verificação deve ser feito **no canônico**, e isso é esperado, não sintoma.

Comandos por alvo (painel, sem transcrever valores):

- **Hostinger (hPanel):** Variáveis de ambiente → editar `BETTER_AUTH_URL` e `AUTH_TRUSTED_ORIGINS`
  → salvar (o salvar já dispara um redeploy — `hpanel-docmap-2026-09-12.md:256`;
  mesmo fluxo já usado em `docs/evidence/hpanel-homologacao-2026-09-12/SESSION-LIMIT.md` §Ação humana, item 4).
- **Vercel (se o interino ainda receber tráfego):** re-salvar as mesmas duas chaves no escopo
  Production + Preview; env nova só vale em deployment novo (efeito no passo 2).

- **Esperado:** as duas chaves presentes e coerentes em **todos** os escopos que servem tráfego.
- **Evidência:** `env-names-after-step1.log` (nomes/estados + escopo; valor **mascarado** pelo painel).
- **FAIL/ABORT:** valor rejeitado pelo painel, chave ausente em algum escopo, ou erro de parse no boot
  (`AUTH_TRUSTED_ORIGINS deve usar HTTPS fora do ambiente local` / `deve conter somente a origem`) ⇒
  **ABORT** — corrigir antes de qualquer nova tentativa.

### 1.5 Passo 4 — SSL no canônico

```bash
curl -sS -o /dev/null -D - https://diretrizprecifica.com/api/health/live | head -20
echo | openssl s_client -connect diretrizprecifica.com:443 -servername diretrizprecifica.com 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates -ext subjectAltName
curl -sS -o /dev/null -D - http://diretrizprecifica.com/ | head -5   # esperado redirect p/ https
```

- **Esperado:** certificado válido **para o host canônico** (SAN cobrindo o que a D-0 decidir: apex e/ou
  `www`), cadeia completa, `notAfter` futuro; HTTP redireciona para HTTPS; sem erro de TLS no `curl`.
  HSTS só é emitido pelo app em produção (`src/start.ts`, citado em `hpanel-docmap-2026-09-12.md:80`).
- **Evidência:** `ssl-<timestamp>.txt` (subject/issuer/dates/SAN — **sem** cookies nem headers de sessão).
- **FAIL/ABORT:** certificado inválido/ausente, SAN não cobrindo o host apontado, ou redirect loop ⇒
  **PARAR** (não se faz probe de auth sobre TLS quebrado) → rollback §2.
- **Pendente declarado:** emissão/renovação automática e cobertura preview↔canônico são pergunta aberta
  de doc oficial (`hpanel-docmap-2026-09-12.md:80`, coluna `PENDENTE`).

### 1.6 Passo 5 — Probes canônicos (o probe de auth é o que PROVA a troca)

```bash
# (a) warm-up: paga o TTFF a frio (baseline: 1683,6/2135,6/2214,8 ms; auto-suspend 304–316 s — cutover-A4.md:301-311)
curl -s -o /dev/null -w '%{http_code} %{time_total}\n' https://diretrizprecifica.com/api/health/live

# (b) asserções com --max-time >= 3 (cold start)
curl -i --max-time 3 https://diretrizprecifica.com/api/health/live     # esperado 200 {"status":"ok"}
curl -i --max-time 3 https://diretrizprecifica.com/api/health/ready    # esperado 200 {"status":"ready","dependencies":{"postgres":"ok"}}

# (c) O PROBE DE AUTH — 200 com corpo `null` em host novo (não 500)
curl -i --max-time 3 https://diretrizprecifica.com/api/auth/get-session
```

Leitura do probe (c) — **CORRIGIDO em 2026-09-13 (S-TEC P1):** o que este probe prova é **apenas** que a
instância de auth **subiu** com uma `BETTER_AUTH_URL` https **válida** — `auth-policy.ts:35-45` exige
apenas existência e origem https pura (o host do **preview** também satisfaz), e o
`originCheckMiddleware` do better-auth **retorna cedo em GET/HEAD/OPTIONS**
(`node_modules/better-auth/dist/api/middlewares/origin-check.mjs:44`), logo `GET /api/auth/get-session`
**não** é validado contra `baseURL`/`trustedOrigins`. **Um `BETTER_AUTH_URL` obsoleto passa verde aqui.**
Portanto: `get-session` ≠ 200 ⇒ **ABORT continua correto** (a instância não subiu); `get-session` = 200
**não é** prova da troca de auth. (Antecedente: o mesmo probe foi o sintoma da cadeia de 4 elos
corrigida em `vercel-prod-fix-2026-09-10.md` §Cadeia causal — ali o alvo era `500 → 200`.)

**Asserção que DISCRIMINA o valor (obrigatória para carimbar a troca de auth):**

- **(c1) Host derivado do `baseURL`:** solicitar reset de senha de conta controlada **pelo canônico** e
  verificar que o **host do link recebido** é o canônico (o critério "e-mail de reset não chegando" já
  existe na §3-0h; aqui ele ganha a checagem explícita de host).
- **(c2) Se `RESEND_*` estiver ausente** (`BLOCKED — env ausente`), a discriminação por e-mail **não
  existe**: nesse caso a troca **não pode** ser carimbada por este probe — registrar
  `auth_baseurl_verified: false` e tratar como critério de abort do 0h, salvo aceite explícito do
  operador registrado no ledger.

Prova adicional (login controlado **no canônico** — sessão `__Host-` não viaja entre hosts):

1. `POST /api/auth/sign-in/email` com `-H "Origin: https://diretrizprecifica.com"` → sucesso; conferir
   `Set-Cookie` com o **nome** `__Host-preco_que_da_lucro.session_token` + `Secure` (não registrar valor).
2. Repetir `get-session` **com** o cookie → JSON de sessão (não `null`).
3. **Controle negativo de origem confiável:** mesmo POST com `Origin` estranho (ex.:
   `https://example.invalid`) ⇒ **deve ser recusado** (esperado 403/INVALID_ORIGIN). Se aceitar ⇒
   **FAIL de segurança → ABORT**.
4. Logout/relogin e acesso sem sessão bloqueado (tabela de autenticação de `cutover-A4.md:349-361`).

Substrate (read-only, op sancionada — sem isso a A5 não abre):

```bash
npm run smoke:substrate   # esperado PASS 7/7: postgres-major 17 · journal-count 12 · journal-hashes 12
                          # · app_runtime sem superuser/BYPASSRLS · tenant-tables-rls · issuer IS NULL = 0
                          # · production-fixture-free 26/26
```

- **Esperado:** `live`/`ready`/`get-session` = **200/200/200** no canônico; login ok; origem estranha
  recusada; `smoke:substrate` 7/7.
- **Evidência:** `probes-canonical-<timestamp>.log` + JSON do smoke + captura do `Set-Cookie` **mascarado**
  (nome do cookie e atributos; valor nunca).
- **FAIL/ABORT:** `get-session` ≠ 200 ⇒ **ABORT** (a instância de auth não subiu); **ausência da
  asserção (c1)** — ou de (c2) sem aceite registrado — ⇒ **não carimbar** a troca de auth;
  `ready` 503 ⇒ bloqueia a janela (`cutover-A4.md:361`); qualquer check do smoke ≠ esperado ⇒ FAIL →
  `m02:forensic-bundle` → ABORT (`cutover-A4.md:363-384`).

### 1.7 Passo 6 — Integridade MX/SPF/DKIM/DMARC pós-associação (o e-mail é o colateral sagrado)

O e-mail transacional é **crítico de auth**: verificação de e-mail e reset de senha dependem de
`RESEND_API_KEY` + `AUTH_EMAIL_FROM` e lançam sem elas (`src/server/email/email-adapter.server.ts:64-72`;
chamadas em `src/server/auth/auth.server.ts:43,52`). MX quebrado = usuários trancados fora; SPF/DKIM/DMARC
quebrados = links de auth caem em spam. O remetente esperado é `noreply@<domínio>` com DKIM/SPF/DMARC
verificados (D-INF-3, `docs/evidence/preflight-rat-2026-09-07/sdd-exec-ps01-add-ops.md:86`).

```bash
# repetir EXATAMENTE o bloco do §1.1 (mesmos seletores DKIM) e comparar byte-a-byte com o "antes"
diff -u docs/evidence/dia-d-2026-09-12/dns-before-<ts>.txt \
        docs/evidence/dia-d-2026-09-12/dns-after-<ts>.txt    # esperado: vazio (tirando o A/CNAME do app)
```

Sondas de estado (sem credenciais):

1. NS/MX/SPF/DKIM/DMARC **inalterados** (diff acima vazio; única diferença admissível: A/CNAME do app).
2. Painel do provedor de e-mail: domínio remetente continua **verified** (captura de tela).
3. Ponta a ponta controlada: solicitar reset de senha de conta controlada **pelo canônico** → e-mail
   chega; o **host do link** deve ser o canônico (prova indireta de que `BETTER_AUTH_URL` está em uso).
4. Logs de auth sem segredo (item 7) e sem `request.failed` novo.

- **Esperado:** todo o conjunto de e-mail intocado; fluxo de reset/verificação funcional no canônico.
- **Evidência:** `dns-after` + `dns-diff` + captura "verified" + recorte **redigido** do link recebido
  (host apenas, token nunca).
- **FAIL/ABORT:** **qualquer** alteração em NS/MX/SPF/DKIM/DMARC, domínio remetente deixando de estar
  verified, ou e-mail de reset não chegando ⇒ **ABORT imediato + rollback §2** (restaurar a zona é
  pré-condição da segurança do e-mail; a associação da web é reversível, o e-mail não é colateral aceitável).
- **Pendência conhecida:** se `RESEND_*` não estiver no alvo (P7 do CP-G2), passos 3–4 ficam marcados
  `BLOCKED — env ausente` e a verificação fica limitada a DNS/painel; **não** marcar PASS.

### 2.1 R3 — rollback app-level (detalhado)

**O que o R3 restaura:** o _artefato servido_ — volta ao build de um SHA anterior, servindo com as
vars de preview restauradas pelo R2. **Não** restaura dado, schema, migration, DNS ou TLS: dado é R5,
zona é R1, e o canônico só volta depois do R4 verde.

**Critérios de invocação (qualquer um, dentro da sequência §2 — R1 → R2 → R3):**

1. `live`/`ready`/`get-session` ≠ 200/200/200 no destino após o redeploy do §1.3 (R4 repetido antes de
   desistir);
2. 5xx sustentado no canônico com banco acessível, ou `ready` 503 persistente (§1.6);
3. qualquer alteração em NS/MX/SPF/DKIM/DMARC, ou domínio remetente deixando de estar `verified`
   (§1.7 → rollback imediato);
4. e-mail de reset/verificação não chegando, quando `RESEND_*` está publicado;
5. `smoke:substrate` ≠ 7/7 ou `issuer_null` ≠ 0 (§3, janela 0h);
6. artefato publicado sem commit identificável (§1.3) — nesse caso o R3 é a própria saída.

**Passos (hPanel; sem rollback por commit):**

| # | Passo | Esperado / prova |
